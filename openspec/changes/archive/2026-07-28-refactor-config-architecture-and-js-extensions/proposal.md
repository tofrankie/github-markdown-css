## Why

当前构建方案已经实现了 slim token、双作用域发布和验证链路，但配置入口、来源注册、主题矩阵、文档元数据与内部构建机制交织在一起，导致维护者新增一个来源或调整一个发布组合时，需要跨越 `build-config`、`utils`、文档和输出约定反复查找。项目尚未发包，现在正是清理结构性负担、把“声明式配置”和“内部实现”拆开的最佳时机。

## What Changes

- 重构构建配置模型，把来源注册、主题元数据、发布矩阵、项目级路径配置从单一构建入口中拆分为职责清晰的声明式配置模块
- 把 token 来源提升为一等配置对象，明确每个来源的 key、类型、路径、用途和扩展方式，降低新增来源时的认知负担
- 调整构建脚本组织，将配置加载、来源收集、token 归属解析、产物生成、验证、写盘等阶段分层，减少 `scripts/utils` 中的隐式耦合
- 重写维护者文档结构，让 `artifacts/README.md` 先给出全局流程，再说明开发、构建、贡献、如何新增配置和相关注意事项
- 统一仓库内 ESM 脚本文件扩展名，从 `.mjs` 调整为 `.js`，避免在一个明确使用 ESM 的项目里继续混用历史扩展约定

## Capabilities

### New Capabilities

- 无

### Modified Capabilities

- `primer-markdown-theme-packages`: 调整配置声明方式、维护者扩展入口、构建脚本组织和维护者文档要求，使新增来源、主题矩阵和发布组合的维护流程更直观、更稳定

## Impact

- 受影响代码主要位于 `scripts/`、`src/`、`artifacts/README.md`、`README.md`、`package.json`
- 需要批量调整仓库内构建脚本文件名与相互引用，从 `.mjs` 统一为 `.js`
- 会影响维护者新增 token 来源、扩展主题矩阵、阅读构建流程和排查验证问题的方式
- npm 对外发布的 CSS 产物目标保持兼容，但内部配置布局、脚本入口和维护者文档会发生明显变化
